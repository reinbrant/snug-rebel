# Changes from staging to latest (as of 11-04-2026)

**Old:** `staging` (order-tracking branch) · **New:** `latest` (fixed branch, 11-04-2026)

**Legend:** ✅ implemented in the code diff · ⚠️ implemented but has a defect or needs verification · ❌ not implemented / still open

---

## 1. Overview

The changes are mostly a **checkout and schema hardening pass**. Total diff: 4 files added, 2 removed, 19 modified (frontend: 2 files; everything else is backend).

Main themes:

- **Checkout rewrite** in `OrderController.Checkout`. It now has server-side shipping fee and discount, atomic stock decrement, a sequence-based order number, idempotency key support, nullable guest orders, and Pending payment and status-history rows.
- **Schema changes.** New `couriers` table, new `orders` columns, nullable `orders._fk_user_id` and `order_status_history.changed_by`, widened ID columns, CHECK constraints, unique/partial indexes, explicit FK delete behaviours.
- **Migrations re-baselined.** The old `InitialCreate` is replaced by a new one, and a hand-run SQL script (`110426_schema_fixes.sql`) is added for the live database.
- **Startup change.** `EnsureCreated()` is removed from `Program.cs`. Nothing creates or migrates the schema at startup any more.
- **Frontend.** The fake-order fallback on checkout failure is removed, the separate `/Address/create` call is removed, and an idempotency key and inline address are sent. The shared guest session token fallback is replaced.

**Headline risks (details in §7 and §8):**

1. `PaymentMethod` enum values were **renumbered** (`CodEwallet` inserted in the middle). Stored integers will be misread.
2. `"COD_EWALLET"` from the frontend **does not parse** to `CodEwallet`, so it falls back to `Cod`.
3. `shipments._fk_courier_id` is **never populated**, because of an inverted condition.
4. The idempotency key is generated per call, so it does not stop a double click.
5. The live DB only works if the SQL script is run **manually**. Without Part 1, cart and checkout inserts will still overflow `varchar(40)`.

What the new migration contains (from the generated code):

- Sequences `order_number_seq` (start 1000) and `product_display_seq`.
- The `couriers` table and the new columns.
- 14 CHECK constraints, created as part of `CreateTable` (these are **validated** constraints, unlike the `NOT VALID` ones in the SQL script).
- `role` is now `integer` (the old model referenced a `user_role` type).

**⚠️ Issues:**

- **Expression indexes are not in the migration.** `ux_users_email_lower` and `ux_promo_code_upper` exist only in the SQL script. The migration has no `migrationBuilder.Sql(...)` calls. A database built from the migration will lack them. The controller now compares promo codes with `ToUpper()`, which relies on that index for performance, not correctness.
- **`xmin` column in the migration.** `Order.Version` is mapped with `.IsRowVersion()`, and the scaffolded `orders` table lists `xmin = table.Column<uint>(type: "xid", rowVersion: true ...)`. `xmin` is a Postgres system column, so whether this applies cleanly on an empty database is **unverified**. Run `dotnet ef database update` against a scratch DB to confirm.
- **Nothing applies the migration automatically.** A fresh database now needs `dotnet ef database update` run manually. The app will start but fail on first query if the schema is missing.

## 3. Backend / API changes

### 3.1 `OrderController.Checkout` (largest change)

| Area | Before | After | Status |
|---|---|---|---|
| Guest handling | Fallback user ID `usr-guest-user` (never in `users`), truncated to 40 chars | `authenticatedUserId` is null for guests. Fake ID and truncation removed | ✅ (depends on DB nullability changes being applied) |
| Contact email | Discarded | Saved to `orders.contact_email`. If a guest sends no email, the placeholder `guest@snugrebel.local` is stored to satisfy `ck_orders_owner` | ⚠️ placeholder data |
| Idempotency | None | Existing order with same key is returned | ⚠️ see below |
| Shipping fee | Taken from the request | Looked up from `couriers` (by code, or name contains), falling back to `jnt`, then to an in-memory J&T 120 | ⚠️ |
| Discount | Taken from the request | Promo looked up (active, window, min order, max uses), percentage/fixed computed, optional `MaxDiscountAmount` cap | ⚠️ |
| Order number | `SR-yyMMdd-Random(1000..9999)` | `SR-yyMMdd-{nextval('order_number_seq')}` | ✅ |
| Stock | `variant.StockQuantity -= qty` (tracked entity) | `ExecuteUpdateAsync ... WHERE stock >= qty`. Zero rows → rollback and 409 `InsufficientStock` | ✅ |
| Promo usage | Not incremented | `times_used + 1` guarded by `max_uses` | ⚠️ result ignored |
| Payment row | None | Pending `Payment` created with parsed method and final total | ⚠️ |
| Status history | None | Pending row created, `ChangedBy` = user or null | ✅ |
| Shipment | Hand-built `ship-` ID, free-text courier | DB default ID, `Courier` = courier name, `FkCourierId` set | ⚠️ see 3.1.3 |
| `IsDefault` on inline address | Always true | True only when a user is signed in | ✅ |

**Defects and unverified points in checkout:**

1. **Payment method parsing.** `Enum.TryParse(request.PaymentMethod, true, ...)` receives `"COD_EWALLET"` from the frontend. The enum member is `CodEwallet`, so parsing fails and the `out` value is the default, `Cod`. E-wallet-on-arrival orders are recorded as plain COD.
2. **Idempotent replay is inconsistent.** The replay path loads the order with `OrderItems` only. `MapToOrderDto` reads `order.Shipments`, so `Courier` will be null on a replay. A concurrent duplicate with the same key hits the unique index and is likely to surface as a 500 (no handling seen).
3. **`FkCourierId` is always null.** The code sets it only when the courier ID does **not** start with `"cour"`, but the DB default for real couriers is `'cour' + uuid`. The condition is inverted, so only the text `Courier` snapshot is saved.
4. **Promo increment is unchecked.** `ExecuteUpdateAsync` returns the affected row count, but the code ignores it. If another request used the last allowed use, the order still succeeds with the discount.
5. **Invalid promos are silently ignored.** An expired, below-minimum or exhausted code results in a zero discount with no error to the client.
6. **Courier lookup.** `IsActive` is not checked. An unknown courier silently becomes J&T instead of being rejected. The `Name.Contains` fallback can match unintended couriers.
7. **Shipping discount.** `Order.ShippingDiscount` is never written (always 0), and the server always charges the full courier fee. The frontend still applies a client-side `SHIPPING_DISCOUNT = 60`, so the confirmation page can show a lower total than what is stored (see §5).
8. **Address is still committed before the transaction.** The inline address `SaveChangesAsync()` runs before `BeginTransactionAsync`. A later failure (for example insufficient stock) leaves an orphan address. Unchanged from before.
9. **`DirectItems` ("Buy Now") is still not read** by the controller, and `CartId`/`BillingAddressId` were removed from the request model. A Buy Now checkout still checks out the whole cart.
10. **Order total depends on the CHECK `ck_orders_money`** (`total = GREATEST(0, subtotal + shipping_fee - discount)`). The code's formula matches. A percentage discount produces 2-decimal rounding, which fits `numeric(10,2)`.
11. **Error responses** in checkout and payment still return `ex.Message` and `stackTrace`. Unchanged.

### 3.2 `PaymentController.ProcessPayment`

- ✅ The Pending-status check now runs inside the transaction (with a rollback on failure).
- ✅ It reuses the Pending payment created at checkout (updates method, status, reference, `PaidAt`) or creates a new one.
- ⚠️ The order is still loaded **before** the transaction and the status check runs on that tracked entity, so it is not a fresh read. Protection against double payment comes from `Order.Version` (xmin concurrency token) and `ux_payments_one_paid`. A conflict will most likely end as a 500 through the generic catch. This is not verified by any test in the provided source.
- ❌ `ChangedBy` is still `order.FkUserId` (null for guests). A rider or admin who marks a payment is not recorded.

### 3.3 `ReviewController.CreateReview`

- ✅ Now verifies the order item belongs to the user (`FkOrder.FkUserId`) and to the product (`FkProductVariant.FkProductId`).
- ✅ Review creation and product `ReviewCount`/`AvgRating` update run in one transaction.
- ❌ No check that the order is `Delivered`.
- ⚠️ The aggregate is recalculated by loading all reviews of the product into memory.
- ❌ Nothing writes `SoldCount`, and nothing in the provided diff reads the new rating columns in the product list (`ProductController` is unchanged).

### 3.4 `CartController`

- ✅ The mutation endpoints (`PUT /Cart/item/{id}` including quantity ≤ 0 removal and variant switch, and `DELETE /Cart/item/{id}`) now return the hydrated cart DTO instead of `{ message }`. This is an **API response shape change** (see §7).
- ✅ `QueryCartWithDetails` uses `AsSplitQuery()`.
- ⚠️ The manual `"c-item" + Guid("N")` ID workaround is removed in `AddToCart`. The DB default (`c-item` + uuid = 42 chars) now applies, which **only works if the column was widened** (SQL Part 1 or the new migration).
- ❌ Unchanged: variants and sizes are still created on the fly with invented stock, there are no ownership checks on item endpoints, and there is no guest-to-user cart merge.

## 4. Frontend changes

Only two files changed (`CheckoutPage.tsx` and `checkout.types.ts` are unchanged).

| File | Change |
|---|---|
| `src/api/checkout.ts` | In non-mock mode, the `try/catch` that logged a warning and fabricated a confirmation is **removed**, so backend errors now reach `CheckoutPage` (which already has a catch that shows `submitError`). The `/Address/create` pre-call is removed. The checkout request carries inline address and contact fields, `cashReadyOption`, and a generated `idempotencyKey` |
| `src/api/session.ts` | Fallback when `localStorage` throws is now a random `sess_<uuid>` instead of the shared constant `sess_fallback_guest` |

**⚠️ Frontend points to verify:**

- **Idempotency key is per call.** It is generated inside `submitCheckoutOrder` on every invocation, so two clicks create two different keys. It only helps if the same key is deliberately reused for retries, which the code does not do.
- **Mock mode is still the default.** `USE_MOCK = VITE_USE_MOCK_API !== "false"`. The fake-order fallback was only removed from the non-mock branch. Unless the env var is exactly `"false"`, no real checkout happens.
- **Money fields are still sent** (`shippingFee`, `discountAmount`) but are ignored by the server. The confirmation screen's totals are computed client-side (courier fee minus the 60 shipping discount, client-validated voucher). They can differ from the stored order. Not checked end to end.
- **Voucher validation** still downloads `/PromoCode` and falls back to hard-coded `REBEL200` / `SNUG100`. The server may reject or ignore a code the client accepted (see 3.1.5).
- **Logged-in users.** `CheckoutPage` passes `owner: { sessionToken }` only, so `userId` is never sent from this page. Orders from signed-in users will be stored as guest orders (null user, placeholder or entered email). Unchanged page, but the new nullable-user behaviour makes it work instead of failing the FK.
- **`cashReadyOption`** is sent as the display label (for example `Custom amount - ₱…`), stored in a `varchar(50)`. Worst-case label length is not checked.
- Cart mutation responses changed shape (§3.4). `CartProvider` was not changed. If it still refetches after each mutation it will work, otherwise check that it tolerates the new payload.
- The `directItems` payload is still sent but ignored by the backend.

## 5. Order of operations for a working environment

This is what the code requires. None of it is automated by the branch.

1. Back up the live database.
2. Run `110426_schema_fixes.sql` Parts 1 to 4 (Part 5 only on non-production). **Part 1 and Part 2 are required** for checkout and add-to-cart to work.
3. Decide how the baseline gets recorded: run Part 6 (or insert the history row yourself) **only after** confirming the live schema matches the migration.
4. For fresh databases: `dotnet ef database update`, then add the two expression indexes manually.
5. Set `VITE_USE_MOCK_API=false` in the frontend environment to exercise the real checkout.

## 7. Breaking changes and integration considerations

1. **`PaymentMethod` renumbering.** Any existing `payments.method` rows, seeds, or external consumers using integer values will now map to the wrong method. Append `CodEwallet` at the end, or migrate stored values.
2. **Cart mutation API shape.** `PUT/DELETE /Cart/item/...` return the cart DTO instead of `{ message }`.
3. **`CreateOrderRequest`** no longer has `CartId` or `BillingAddressId`. Extra fields from clients are simply ignored. `shippingFee` and `discountAmount` are ignored.
4. **`OrderDTO`** gained fields and `FkUserId` is nullable. Clients that assume a non-null user ID need updating.
5. **Startup no longer touches the schema.** Environments (teammates, CI, new Neon branches) must run migrations or the SQL manually.
6. **Orders can have a null user.** Any query, report, or code that joins `orders → users` or reads `order.FkUser` needs null handling. `GET /Order/user/{id}` will not list guest orders.
7. **Behaviour changes:** the address delete is now a soft delete, order status history is `Pending` at creation, the order total shown to the user may differ from the stored total when the client applies a shipping discount, and `Conflict (409)` is a new checkout response for stock problems.
8. **Dashboard** still counts `is_test` orders.

## 9. Summary

`latest` makes checkout materially safer than `staging`: the server now prices shipping, validates and caps discounts (with gaps), decrements stock atomically, generates collision-free order numbers, supports guest orders, and writes Pending payment and history rows. Several supporting database changes (nullable users, widened IDs, constraints, couriers, indexes) are in place in the model, the new migration, and a manual SQL script.

The work is **not complete**. The enum renumbering, the e-wallet mapping, the courier FK condition, the unchecked promo increment, and the per-call idempotency key are defects introduced or left in this branch. Buy Now, authentication, cart ownership, and the live-database rollout steps remain open. Because startup no longer creates or migrates the schema, a developer taking this over must apply the SQL script (or the migration) manually and verify the points in §8 before relying on the new checkout flow.
